## Зачем этап

Сейчас текст реплики получается так: после конца записи файл m4a уходит в `gpt-transcribe`. Это
0,6–2,0 с (в S03c), а в плохой день до 6,8 с (D62). Точность на записях пользователя — 85 % слов. Ошибка
распознавания бьёт дважды: учитель отвечает не на то, а поправщик поправляет то, чего ученик не
говорил.

Проба S03b: `gpt-live-transcribe` с `delay: low` — 92 % слов, текст через 0,46 с (p90 0,58) после
`commit` (D67). Звук идёт потоком во время записи. Конец реплики по-прежнему решает Silero на
устройстве: VAD сервера у этой модели нет.

Кроме того, S04 понадобится **частичный текст** во время записи, чтобы понять, закончена ли мысль. Этот
этап его не использует, но должен сделать доступным.

## Что сделать

### 0. Молчание с начала — 8 с (D70)

`ModelConfig`: если речи с начала записи не было, запись кончается через **8000 мс**, а не 3000.
- После речи — по-прежнему 3000 мс.
- Пульс звучит как сейчас.
- Тесты детектора — на оба числа.

### 1. Поток в `gpt-live-transcribe` (D67)

**Сессия.** Сессия распознавания Realtime: модель `gpt-live-transcribe` (имя — в `ModelConfig.kt`),
`delay: low`, язык `en`, `turn_detection: null`.
- **Контекст** (`TranscriptionPrompt`: контекст + последняя фраза учителя) — передать, если модель его
  принимает. Проверь по документации и пробой. Если не принимает — записать это в отчёт; точность
  сравнить с файлом с контекстом.
- **Формат звука** — какой требует сессия. Если нужен 24 кГц, пересэмплировать 16 → 24 кГц, как в пробе.
  Сам звук записи не меняется: 16 кГц для Silero и для файла.

**Когда открывать.** Первые слова не должны теряться, а соединение не должно добавлять задержку.
- Откройте сессию заранее — например, когда учитель заговорил или когда запись готовится — или держите
  одну сессию на весь разговор с `commit` и `clear` на каждой реплике.
- Выбери сам и объясни в отчёте.
- Учти пределы сессии: время жизни, простой.
- Звук, записанный, пока соединение ещё открывается, копится и уходит сразу после открытия.

**Звук идёт потоком** с первого кадра записи и до её конца: конец по тишине, кнопка или предел 90 с.

**Конец реплики.**
- Речь была (`heardSpeech`) — `commit`, ждать `completed`.
- Речи не было — `clear` без `commit`: ничего не распознаётся. Как сейчас, транскрипции нет.

**Ожидание текста** — с пределом, например 2,5 с; число — в `ModelConfig`. Не пришёл — запасной путь.

**Частичный текст.** События дельт складываются в частичный текст текущей реплики. Его можно получить
из контроллера (поток или колбэк для S04). В журнал идёт только число дельт, не текст.

### 2. Запасной путь — файл (как сейчас)

- Запись по-прежнему пишется целиком: m4a для файла, копия для отладки — как сейчас.
- **Сбой потока — в любой момент:**
  - не открылась сессия;
  - разрыв во время записи;
  - нет текста к пределу;
  - ошибка сервера.

  В любом из этих случаев текст берётся из файла нынешним путём.
- **Без повтора потока**, сразу файл. Для файла правила повтора прежние: D30, без повтора на квоте.
- Если до этого запасной путь кончился «нет звука», ничего не меняется.

### 3. Сверка в debug (без текстов в журнале)

- В debug-сборке, пока включён флаг в `ModelConfig`, для каждой реплики параллельно идёт и файл.
- В журнал — `live vs file: similarity 0.NN (N vs M words)`, где similarity — доля совпавших слов. Сами
  тексты — нет.
- Тексты для сверки архитектором можно положить в `diagnostics/` на телефоне рядом с копиями записи (вне
  Git, `tools/pull-log.sh` или `pull-recordings.sh`, на твой выбор).
- В release флага нет.

### 4. Журнал

- `[Network] live transcription: session open in N ms (reused | new), audio N s sent, commit → text N ms,
  N deltas, N chars; cost $…`.
- `[Network] live transcription failed (причина) → file`.
- `[Timing]`:
  - `stt` — как прежде: от конца записи до готового текста;
  - новое поле `stt_path=live | file`.

### 5. Проверка на записях S03b

Записи лежат в `diagnostics/` у тебя с прошлых этапов. Если их нет — попроси архив у пользователя. В Git
не класть (D69).

- Прогнать **код приложения** — сессию, `commit` и запасной путь — на 48 записях. Например, JVM-тест с
  настоящим ключом, который пропускается без папки и без ключа, или инструмент. Звук подавать в темпе
  реального времени, конец — по Silero приложения (3000 мс тишины).
- Меры:
  - точность против текста сценария;
  - `commit → text`: медиана, p90;
  - доля запасного пути;
  - цена.
- Цели:
  - точность не ниже 90 % в сумме и не ниже, чем у файла, в каждом условии;
  - `commit → text`: медиана ≤ 0,6 с, p90 ≤ 1,0 с;
  - запасной путь — 0 на здоровой сети.
- Сверить с пробой S03b: там `commit` был через 1 с после речи, теперь — через 3 с, а в хвосте шум.
  Проверить, не дописывает ли модель лишнего из шума.
- Бюджет — до $1, подтверждение перед запуском.

## Ручная проверка — подсказки для раздела в отчёте

- **Обычный разговор.** Ответы как раньше, текст твоей реплики на экране — точнее.
- **Пауза перед ответом.** После «говори» молчите 5–6 с, потом ответьте. Запись не кончилась, учитель
  ответил.
- **Молчание.** После «говори» молчите → через ≈ 8 с «ничего не услышал».
- **Сеть пропала.** Во время записи включите режим полёта на 2 с и выключите. Ответ всё равно пришёл: в
  журнале `failed … → file` или ошибка сети, как раньше.

Архитектор проверит по журналу:
- `stt_path=live` и `commit → text`;
- `live vs file: similarity`;
- `[Timing] audible` — ожидается быстрее нынешних 3,4 с на величину `stt`.
