## Зачем этап

Поиск сломан (DuckDuckGo, D32), а путь с поиском — самый медленный (≈ 8 с по журналу S03, цель
≤ 6 с). Проба S02c показала решение (D36–D40): Responses API, встроенный `web_search`, потоковый
ответ. Без поиска первая группа готова через 0,76 с вместо 1,12 с, с поиском — через 3,8 с, и
данные есть во всех ответах.

## Что сделать

### 1. `ResponsesTutor` (D36)

- Реализация `Tutor` на `POST /v1/responses`: `gpt-6-luna`, `reasoning.effort: none`, `stream: true`,
  `tools: [{type: "web_search", search_context_size: "low"}]`. Всё — в `ModelConfig.kt`.
  Работающий образец — `tools/probe/probe.py`, подкоманда `responses`, вариант 3.
- `store: false`; историю приложение хранит и шлёт само (окно D27). В историю идут только реплики
  ученика и ответы учителя (вычищенный текст), служебные элементы поиска — нет. Значит, пары
  «вызов — ответ инструмента» больше не нужно беречь при обрезке — упрости `trimHistory`.
- Системный промпт: искать только ради свежих фактов (цены, новости, погода, спорт, расписания,
  время событий), не ради обычного разговора — в пробе учитель без нужды не искал ни разу, сохрани
  это. Если поиск ничего не дал — честно сказать (правило S02b остаётся). Дату в промпте оставить.
- Удалить `ChatTutor`, `WebTools`, `ToolResults`, `get_weather`, разбор DuckDuckGo и обращения к
  wttr.in. Интерфейс `Tutor` меняется: ответ — поток событий (куски текста, начало и конец поиска,
  источники, конец ответа с `usage`). Обнови его описание в отчёте.
- Повтор (S02b) — только если ни одна группа ещё не прозвучала. Если поток оборвался, когда учитель
  уже говорит: дочитать готовые группы, затем «ошибка», фраза голосом телефона и «конец».

### 2. Сноски (D37)

- Перенести `clean_for_speech` из пробы в Kotlin: ссылки markdown, голые адреса, `utm_source` — до
  нарезки. Тесты — на примерах сносок из `02c-results.md`.
- На экране под ответом — источники кликабельными ссылками (заголовок → адрес из `annotations`).
  Метку `(Live Web Data):` заменить этим. Голосом источники не читаются.

### 3. Потоковая нарезка (D38)

- Обёртка над `SpeechPlanner` по правилу из раздела «Как в S02d подавать поток в `SpeechPlanner`»
  в `02c-results.md`. Сам `SpeechPlanner` не меняется.
- **Пауза после группы определяется позже:** группа уходит в синтез с текстом, а пауза после неё
  уточняется, когда пришло продолжение (или ответ кончился). Пауза нужна только после того, как
  группа прозвучит, а к этому времени текст уже есть. Это убирает расхождения пауз, которые нашла
  проба (5 из 63: 600 мс вместо 1600 мс перед абзацем).
- Если текст уже отданной группы разошёлся с итоговой нарезкой — строка в журнал.
- Тест: ответы из приложения `02c-results.md` (сырые потоки пробы в репозиторий не попали), нарезанные
  на куски разного размера, в том числе по одному знаку, дают ту же нарезку, что готовый текст, —
  и текст групп, и паузы.
- `SpeechPipeline` получает группы потоком, а не списком; опережение 3 и порядок (S02) сохраняются.
- Текст на экране растёт по мере ответа.
- Python-копию `tools/probe/speech_planner.py` поправить так же, если правило изменилось.

### 4. Фраза на время поиска (D39)

- Когда поток сообщил о начале поиска и учитель ещё ничего не сказал — короткая заготовленная фраза
  голосом учителя: «Let me check.» (одна-две на выбор, без случайных длинных). Синтезировать её
  один раз за жизнь сервиса через Realtime и держать в памяти; если ещё не готова — пропустить.
- «Тик» ожидания после фразы — как сейчас. Если поиск закончился раньше, чем фраза прозвучала, —
  фразу не обрывать, первая группа ответа идёт после неё.

### 5. Журнал и замер

- `[Timing]`: `first_token` (первый кусок текста учителя), `first_group` (первая группа ушла в синтез),
  `search=yes|no`, `search_ms`, `filler=yes|no`; остальное как в S02b.
- По каждому ответу: токены (`usage`), число вызовов поиска, типы источников (`oai-weather` и т. п.),
  оценка цены ответа. Без текстов и адресов.
- Расхождения потоковой нарезки — отдельной строкой.
