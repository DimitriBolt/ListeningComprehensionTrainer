### 1. Поток в `gpt-live-transcribe` (D67)
Документация OpenAI «Realtime transcription» прочитана 2026-11-26. Отдельно проверено короткой пробой с ключом
(≈ $0,01, `/tmp`, в репозиторий не клал).

**Что подтвердилось**
- **Контекст модель принимает.** `audio.input.transcription.prompt` сервер возвращает в `session.updated`.
- **`prompt` меняется посреди сессии** через `session.update` перед репликой. Поэтому контекст (`TranscriptionPrompt`:
  контекст + последняя фраза учителя) — тот же, что у файла, и обновляется на каждой реплике.
- **`input_audio_buffer.clear` → `cleared`.** `commit` пустого буфера — ошибка `input_audio_buffer_commit_empty` (нужно
  ≥ 100 мс). У нас `commit` только при речи ≥ 200 мс.
- **Дельты идут во время записи** с `item_id`. Тот же `item_id` потом приходит в `committed` и `completed`.
- **`completed` несёт `usage.seconds`** — по нему считается цена.
- **Сессия живёт 60 мин** (`expires_at`).
- **Цена — $0,017 за минуту** (страница модели).
- **Звук — только PCM 24 кГц.** Пересэмплирование 16 → 24 кГц на лету делает `Resampler16To24` (чистый Kotlin). Это тот
  же фильтр, что `resample_poly(x, 3, 2)` пробы S03b (Kaiser β = 5, 61 коэффициент). Golden-тест против SciPy:
  расхождение ≤ 1 на отсчёт. Запись по-прежнему 16 кГц для Silero и для файла.

**Когда открывать сессию — одна на весь разговор**
- **Открывается заранее**: `prepare()` при старте сервиса и в начале каждого хода, до сигнала «говори».
- **Служит реплике за репликой.** Перед репликой — `session.update` с её `prompt`, в конце — `commit` или `clear`.
  Соединение (≈ 1,2 с в прогоне) не попадает ни в одну реплику, кроме первой после обрыва. Но и тогда звук не теряется:
  он копится в очереди сокета OkHttp и уходит сразу после открытия. В прогоне три такие реплики распознаны на 100 %.
- **Пределы:**
  - сессия обновляется между репликами через 50 мин (`LIVE_SESSION_RENEW_MS`), посреди реплики — никогда;
  - простой не стоит денег (платится звук), живость проверяет ping каждые 20 с, как у синтеза;
  - сервис без разговора закрывается через 10 мин (D18), сессия — вместе с ним.
- **После сбоя** (ошибка сервера, нет текста к пределу) сессия закрывается, следующая реплика открывает новую.

**Как идёт реплика**
- **Звук** идёт с первого куска записи до её конца (тишина, кнопка или 90 с) через `AudioSink` в
  `AudioInput.record`.
- **Конец** уходит в поток сразу, до дожимания m4a: речь была — `commit`, не было — `clear`, транскрипции нет.
- **Ожидание текста** — `LIVE_TEXT_TIMEOUT_MS = 2500` от `commit`.
- **События узнаются по `item_id`.** Опоздавшие дельты и `completed` прошлой реплики к новой не попадают. Если `completed`
  пришёл раньше `committed`, он ждёт `committed`.
- **Частичный текст** собирается из дельт и доступен как `ConversationController.partialText` (`StateFlow`). С начала
  каждой записи он пустой, на экран и в журнал не идёт — это заготовка для S04. В журнал идёт только число дельт.

Код:
- `conversation/LiveTranscription.kt` — интерфейсы `LiveTranscriber`, `LiveTurn`, `AudioSink`, `LiveResult`, `LiveStats`;
- `openai/RealtimeTranscriber.kt` — сессия и реплика, сокет за интерфейсом `LiveSocketFactory`;
- `openai/LiveTranscriptionEvents.kt` — события;
- `audio/Resampler16To24.kt`.

### 2. Запасной путь — файл
- **Запись** пишется как раньше: WAV, m4a и копия для отладки.
- **Любой сбой потока — сразу файл**, поток не повторяется. Сбоями считаются:
  - сессия не открылась к пределу;
  - разрыв в любой момент (дальше звук не шлётся);
  - нет текста к пределу;
  - `error` или `…transcription.failed` от сервера.
- Файл идёт нынешним `FileTranscriber`: правила повтора прежние, D30, без повтора на квоте.
- Если и файл не дал текста — «ошибка распознавания», как раньше.
- **Пустой текст из потока** — это текст, а не сбой: дальше, как у файла, «молчание» (см. отклонения).

### 3. Сверка в debug
- `ModelConfig.LIVE_COMPARE_WITH_FILE_IN_DEBUG = true`. Действует только при `BuildConfig.DEBUG`, в release сверки нет.
- Файл идёт параллельно с потоком, в области сервиса: ответ учителя его не ждёт.
- В журнал — `[Network] live vs file: similarity 0.NN (N vs M words)`. Похожесть — доля совпавших слов: общая
  подпоследовательность слов, делённая на слова более длинного текста (`TranscriptMatch`).
- Тексты — в `files/diagnostics/live_vs_file.jsonl` на телефоне (последние 200). `tools/pull-log.sh` теперь забирает
  этот файл в `diagnostics/live_vs_file.jsonl` (вне Git).
- Если поток дал сбой, в debug текст берётся из уже идущего файла.

### 4. Журнал
- `[Network] live transcription: session open in N ms (reused | new), audio N.N s sent, commit → text N ms, N deltas, N chars; cost $0.NNNNN`
  - `session open in N ms` — сколько звук реплики ждал открытия сессии (0 — уже была открыта);
  - `reused` — сессия служила прошлой реплике;
  - время самого соединения — отдельной строкой `[Network] live transcription session open in N ms`.
- `[Network] live transcription failed (причина) → file`. Причины: `session not opened in N ms`, `closed: …`,
  `no text in 2500 ms`, `error тип/код`, `transcription failed (…)`, `send failed`.
- `[Network] live transcription session closed: причина (open N ms)`.
- `[Timing]`:
  - `stt` — как прежде: от конца записи (с учётом `enc`) до готового текста;
  - в конце строки — новое поле `stt_path=live | file`.

## Отклонения от брифа
- **В прогоне п. 5 ложный конец на паузе обдумывания запись не останавливал.**
  - Такой конец был в 23 записях из 40 (D65, задача S04).
  - Если остановить запись на паузе, точность мерилась бы на половине фразы, и сравнения с пробой не было бы.
  - Поэтому запись шла до первого конца Silero **после** конца речи по разметке S03b. Так получается ровно то, что просил
    бриф: `commit` через 3 с после речи, с шумом в хвосте.
  - Сам конец — код приложения, без изменений.
- **Файл в прогоне — WAV, а не m4a.** На JVM нет `MediaCodec`, а сжатие делает именно он. Возможно, отсюда разница с пробой
  S03b у файла (95 % против 85 %) — см. «Замечено».
- **Пустой текст из потока — не сбой.** Пустой `completed` значит, что модель ничего не разобрала. Дальше, как у файла:
  меньше 2 знаков — «молчание». Иначе на шорохе, который Silero принял за речь, платили бы ещё и за файл. В прогоне пустых
  текстов не было.
- **`session open in N ms` в строке журнала** — это сколько звук реплики ждал сессию (0, если открыта), а не время
  соединения. Время соединения — в своей строке `live transcription session open in N ms`.
- **`delay: low` сервер в `session.updated` не повторяет** (повторяет `model`, `languages`, `prompt`). Так было и в пробе
  S03b. Что `low` действует, видно только по результату: время и точность — как у `low` в пробе.

## Ручная проверка для пользователя
1. **(обязательно)** Сборка с нуля: `./gradlew clean installDebug` (или «Build → Clean Project», затем «Run»). Приложение
   запускается.
2. **(обязательно) Обычный разговор.**
   - Нажмите «Talk to Teacher 🎙️» (или среднюю кнопку гарнитуры) → «говори».
   - Скажите фразу («I like to read books in the evening.») и молчите → примерно через 3 с «обрабатываю», учитель отвечает.
   - Ответ как раньше; пауза до голоса учителя — не длиннее, скорее короче. Текст вашей реплики на экране — точнее.
   - Повторите 4–5 раз, можно в авто-режиме.
3. **(обязательно) Пауза перед ответом.** «Talk to Teacher 🎙️» → «говори», молчите 5–6 с (два-три «тук»), потом скажите
   фразу и молчите → запись не кончилась на паузе, учитель ответил.
4. **(обязательно) Молчание.** «Talk to Teacher 🎙️» → «говори» и молчите → примерно на четвёртом «тук» (≈ 8 с) сигнал
   «ничего не услышал». Учитель не отвечает. Раньше было ≈ 3 с.
5. **(обязательно) Сеть пропала.**
   - «Talk to Teacher 🎙️», начните говорить фразу, включите режим полёта, через 2 с выключите, договорите фразу и молчите.
   - Ответ всё равно пришёл, может на 1–3 с позже обычного.
   - Если к концу фразы сеть ещё не вернулась, возможны «ошибка» и голосовое сообщение телефона, как раньше без сети. Тогда
     повторите шаг: включение сети занимает несколько секунд.
6. (желательно) **Кнопка.** «Talk to Teacher 🎙️», скажите фразу и сразу нажмите «Stop Recording» (или среднюю кнопку
   гарнитуры) → «обрабатываю» сразу, учитель отвечает.
7. **(обязательно)** Запустите `tools/pull-log.sh` и пришлите в чат архитектора `diagnostics/latest.log` и
   `diagnostics/live_vs_file.jsonl`. Во втором — тексты ваших реплик из потока и из файла, для сверки.

Что архитектор проверит по журналу:
- `[Network] live transcription session open in N ms` — при старте сервиса;
- `[Network] live transcription: session open in 0 ms (reused), …, commit → text N ms` на шагах 2, 3, 6;
- `[Timing] … stt=N … stt_path=live` и `audible` — ожидается меньше 3,4 с (S03c) примерно на разницу `stt`;
- `[Network] live vs file: similarity 0.NN (N vs M words)`;
- шаг 4: `recording: ≈ 8000 ms, speech 0 ms … ended by silence` и `counted as silence: yes`, строк `live transcription`
  нет;
- шаг 5: `live transcription session closed: …` и `live transcription failed (closed: …) → file`, затем `stt_path=file`.
  Если файл тоже не прошёл — `circle end: TRANSCRIPTION_ERROR`, как раньше без сети.
