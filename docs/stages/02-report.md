# Отчёт S02 — Синтез на Realtime

## Сделано

### 1. `RealtimeSynthesizer` (`openai/RealtimeSynthesizer.kt`, события — `openai/RealtimeEvents.kt`)
- WebSocket к Realtime API через уже подключённый OkHttp, без новых зависимостей. Модель
  `gpt-realtime-2.1-mini`, голос `verse`, скорость 0.88, звук PCM 24 кГц, «Промпт 1», без VAD.
  Всё это лежит в `ModelConfig.kt` (`SPEECH_*`).
- Каждая группа — отдельный ответ вне разговора (`conversation: "none"`): на входе только текст
  группы, на выходе только звук, в `metadata` — номер группы. Протокол как в `tools/probe/probe.py`,
  сверен с документацией OpenAI «Realtime conversations» (ответы вне разговора; сессия не дольше 60 мин).
- **Сессия открывается заранее:** при старте сервиса и в начале каждой записи ученика (`prepare()`).
  Пока ученик говорит, оборванная сессия успевает переподключиться. Одна сессия на время жизни
  сервиса; между ответами она обновляется после 50 минут (`SPEECH_SESSION_RENEW_MS`); закрывается в
  `onDestroy`. Если ответ на группу прерван («Stop», «Back», таймаут), сокет закрывается, и обрывок
  старого ответа не смешается со следующим.
- Ответы на группы идут по одному на сессию: документация не говорит, сколько ответов вне разговора
  можно вести параллельно. По пробам группа готова за ≈ 0,5 с, а звучит 1–3 с, так что опережение
  успевает.
- **Недоступность** (`unavailable`): ошибка сети, HTTP 401/429 при подключении, закрытие сервером
  (`invalid_api_key`), коды `rate_limit_exceeded`, `insufficient_quota` и т. п., подключение дольше 5 с,
  ответ дольше 8 с. **Ошибка одной группы** (не `unavailable`): `server_error`, ответ без звука,
  статус не `completed`.
- Каждая группа пишется в журнал строкой `[Network] realtime group: first audio N ms, done N ms,
  tokens in text … (cached …) audio …, out text … audio …` — это токены из `response.done`.

### 2. Запасной синтез — `audio/AndroidTtsSynthesizer.kt`
- Встроенный `TextToSpeech`: `Locale.US`, скорость 0.88. Звук берётся через `synthesizeToFile`
  (WAV, разбор — `audio/WavPcm.kt`), поэтому проходит ту же нормализацию громкости и тот же
  проигрыватель, что и Realtime.
- Движок поднимается заранее, при старте сервиса, в фоне. В журнале строка
  `android tts ready in N ms (engine …)` или `android tts unavailable: no English voice data` /
  `English not supported` / `engine init failed`. Нет движка или английского голоса — это ошибка
  синтеза: «ошибка» + «конец», причина в журнале. Если движок не поднялся, при следующей группе он
  пробует подняться заново.
- **Для S02b (D21):** `synthesize(text)` отдаёт PCM, играет его обычный `AudioOutput.play`. Голосовое
  сообщение об ошибке — это вызов `synthesize` и `play`, без изменений в классе.

### 3. Группы по порядку, первая — первой (`conversation/SpeechPipeline.kt`, чистый Kotlin)
- Первая группа запрашивается сразу после ответа учителя и ничего не ждёт. Дальше готовыми держатся
  не больше 3 групп вперёд (`SPEECH_LOOKAHEAD = 3`). Прежняя очередь «все группы сразу» (до 80
  запросов) и `MAX_PARALLEL_REQUESTS` удалены.
- Сверка: расшифровка `output_audio_transcript.done` сравнивается с текстом группы после
  нормализации, как в пробах (`conversation/TranscriptCheck.kt` — перенос `compare_texts`: регистр,
  пунктуация, `**`, числа словами и цифрами, `$`, `%`, сокращения).
- Расхождение или ошибка → один повтор → снова не так → **эта группа** читается запасным синтезом,
  следующая снова идёт через Realtime. Realtime недоступен → **остаток ответа** читает запасной
  синтез, следующий ответ снова начинается с Realtime.
- Группа играет **целиком** (согласовано с пользователем): так ошибочная группа не прозвучит до
  сверки. По пробам S00b это стоит ≈ 0,1 с на первой группе (первый звук 0,43 с, весь звук 0,54 с,
  медианы).
- Паузы между группами — строго по эталону. «Stop» и «Back» отменяют корутину круга: обрывается
  воспроизведение и синтез, Realtime закрывает незаконченный ответ (тест
  `Stop during speech stops playback and pending synthesis`).

### 4. Щит Bluetooth только для Bluetooth (D17)
- Щит — нули в `AudioTrack` перед каждой группой (`AudioOutput.play(audio, shieldMs)`), а не
  синтезированные точки.
- Перед каждым ответом `AudioOutput.prepareReply()` смотрит, куда идёт звук. На Android 13+ это
  точный ответ системы (`getAudioDevicesForAttributes`), на старых версиях — подключённые выходы
  по приоритету Bluetooth → usb → wired → динамик. Строка журнала:
  `[Audio] reply output: usb, shield 0 ms`.
- Bluetooth (A2DP, SCO, LE, слуховой аппарат) → 1200 мс; `usb`, `wired`, динамик, HDMI → 0;
  неизвестный выход → 1200 (лучше лишняя секунда, чем съеденный слог). Решение принимает
  `audio/OutputKind.kt` (`BluetoothShield`).
- Следующая группа запускается на `shieldMs` раньше эталонной паузы (не меньше 10 мс). Без щита
  паузы ровно по эталону, со щитом расчёт тот же, что был.

### 5. Громкость (`audio/Loudness.kt`, чистый Kotlin)
- По каждой группе в журнале RMS и пик в дБFS до и после нормализации. RMS считается только по
  звучащим окнам 20 мс: тишина по краям и паузы его не занижают.
- Нормализация: усиление до RMS −16 дБFS (не больше +24 дБ, чтобы не вытягивать шум), затем
  ограничитель пика с потолком −1 дБFS. Огибающая плавно опускается за 5 мс до пика и возвращается
  за 80 мс, края группы затухают за 3 мс. Перегрузки и щелчков нет, это проверено тестами. Значения —
  `SPEECH_TARGET_RMS_DBFS`, `SPEECH_PEAK_CEILING_DBFS`, `SPEECH_MAX_GAIN_DB`.
- Сигналы: `CueTones.LOUD` 0.25 → **0.14** (RMS ≈ −20 дБFS, на 4 дБ тише голоса), `QUIET`
  0.08 → **0.044** («тик» на 10 дБ тише остальных сигналов, как было).
- Поток: голос — `AudioTrack` с `USAGE_MEDIA` / `CONTENT_TYPE_SPEECH`, сигналы — `USAGE_MEDIA`
  (как и были), аудиофокус — `USAGE_MEDIA`. **Как было:** `MediaPlayer` без `setAudioAttributes`,
  то есть поток по умолчанию `STREAM_MUSIC` — тоже медиа. Значит, тихий звук объяснялся не потоком, а
  уровнем самого звука `tts-1` без нормализации. Уровень `tts-1` не измерен: ключа в этой среде нет.

### 6. Журнал
- Каждый сыгранный сигнал — строка в момент, когда он начинает звучать: `[Audio] cue: LISTEN`,
  `cue: END` и т. д. (`CuePlayer`).
- По каждой группе: `[Audio] group 3/12: realtime, ready in 512 ms, 1820 ms of audio,
  rms -22.1 dBFS, peak -6.0 dBFS -> rms -16.0 dBFS, peak -1.0 dBFS (gain 6.1 dB)`. Вместо `realtime`
  может стоять `realtime (attempt 2)` или `android`. Расхождение пишется так:
  `group 3/12: realtime mismatch (mismatch: expected 4 words, heard 5), attempt 1 of 2`. Переход:
  `group 3/12: fallback to android after 2 attempts` или
  `realtime unavailable (http 401): group 3/12 and the rest of the reply via android`. Тексты
  групп и расшифровки в журнал не пишутся, только номера, длины и числа слов.
- `[Timing] stt=… tutor=… first_audio=… audible=…`: `audible` — момент, когда голос **слышен**
  (`first_audio` + щит).
- `onTrimMemory` пишется только при смене уровня: `onTrimMemory level=20 (was -)`.

## Отклонения от брифа
- **Группа играет целиком, а не по первым кускам.** Бриф это допускает, пользователь согласился.
  Цена ≈ 0,1 с на первой группе, зато сверка идёт до воспроизведения.
- **`SpeechAudio` — один класс PCM** (`pcm`, `sampleRate`), а не новый вариант рядом со старым:
  вариант MP3 удалён вместе с `tts-1`.
- **Щит перенесён из `Synthesizer` в `AudioOutput`.** Вместо `Synthesizer.leadInMs` теперь
  `AudioOutput.prepareReply(): Long` и `play(audio, shieldMs, onStarted)`: нужен ли щит, зависит
  от выхода звука, а не от синтезатора. У `Synthesizer` теперь `name`, `prepare()`, `release()`, а
  `synthesize()` возвращает `SynthesizedSpeech` (звук + расшифровка). Предлагаю так и записать в
  `ARCHITECTURE.md`.
- **Щит на Bluetooth — ровно 1200 мс тишины и запуск на 1200 мс раньше.** Раньше было ≈ 1,2 с
  тишины и запуск на 1000 мс раньше, поэтому длинные паузы на Bluetooth выходили на 200 мс длиннее
  эталона (абзац 1800 вместо 1600). Теперь паузы от 1200 мс ровно по эталону; короткие паузы, как и
  раньше, ≈ 1210 мс. На проводных щита нет совсем.
- **Добавлены `dataExtractionRules`** (Android 12+): один `allowBackup="false"` не запрещает перенос
  данных на новый телефон, а D20 про то, чтобы ключ не уходил с устройства.
- **Запасной синтез используется и при ошибке одной группы.** Бриф говорит «ошибка → повтор →
  запасной» для группы; так и сделано, но ошибкой считается и ответ Realtime без звука.

### Формула для архитектора («конец записи → голос слышен»)
- Строка: `[Timing] stt=… tutor=… first_audio=… audible=…`. Число `audible` — миллисекунды от конца
  записи ученика до момента, когда голос слышен (после щита, если он был). Строка одна на круг
  ученика, у прощания её нет.
- **Медиана и худший случай** — по всем `audible` журнала.
- **С поиском / без:** круг с поиском — если между предыдущей строкой
  `[Controller] Listening -> Thinking (recording finished)` и этой `[Timing]` есть
  `[Network] GET duckduckgo.com`.
- **Сравнение с S01b:** там `audible` не было. Слышимый голос в S01b ≈ `first_audio` + 1200 мс
  (тишина в начале файла `tts-1`).
- Разложение: `audible − tutor` — синтез первой группы плюс щит; `first_audio − tutor` —
  `ready in` первой группы (строка `[Audio] group 1/N`).
- Проверить по журналу: `[Audio] reply output: usb, shield 0 ms` → `audible = first_audio`.

### Стоимость 10-минутного занятия (оценка)
- На группу по пробе S00b (50 групп, промпт 1): вход ≈ 82 текстовых токена (из них 64 из кэша),
  выход ≈ 35 токенов текста (расшифровка) и ≈ 30 токенов звука; $0,0391 за 50 групп ≈
  **$0,0008 за группу**. Цены — как в `tools/probe/probe.py` (S00b): вход текст $0,60, выход текст
  $2,40, выход звук $20 за 1 млн токенов; кэш не учтён, то есть оценка сверху. **Цены надо сверить с
  текущей страницей OpenAI.**
- Занятие 10 мин: круг ≈ 45–60 с (реплика 10–40 с, ожидание, ответ 10–15 групп) → 10–13 кругов,
  100–200 групп → **≈ $0,08–0,16** за синтез; повторы при расхождении добавляют по группе.
  Открытая сессия без ответов токенов не тратит. Для сравнения: `tts-1` по тем же ответам
  (≈ 3–4 тыс. символов) — ≈ $0,05–0,06.
- **По журналу пользователя:** сумма по строкам `[Network] realtime group: … tokens in text A
  (cached C) audio B, out text D audio E` →
  `(A·0,60 + B·10 + D·2,40 + E·20) / 1 000 000` долларов (цены S00b; кэш C дешевле — если цена
  кэша известна, вычесть).

экране «Listening Practice».

1. **(обязательно) Обычный разговор.** Нажать «Talk to Teacher 🎙️» → звучит сигнал начала записи →
   спросить «How are you today?» → звучит сигнал «обрабатываю» → учитель отвечает голосом `verse`, с
   паузами между короткими кусками, как раньше. Первое слово каждого куска слышно целиком. После
   последнего слова — сигнал конца ответа.
2. **(обязательно) Длинный ответ.** «Talk to Teacher 🎙️» → «Give me five tips to improve my
   listening, as a numbered list.» → учитель читает весь список по порядку, номер пункта звучит вместе
   с заголовком, ни один пункт не пропущен, лишних долгих пауз посреди ответа нет. На слух весь ответ
   одним и тем же голосом.
3. **(обязательно) Громкость.** Поставьте громкость телефона так, чтобы YouTube (любой разговорный
   ролик) звучал удобно. Не трогая громкость, задайте учителю вопрос → учитель звучит **примерно так же
   громко**, как YouTube, без хрипа. Сигналы чуть тише голоса учителя. Кнопки громкости телефона во
   время ответа учителя делают его тише и громче, как музыку.
4. **(обязательно) «Stop ⏹» посреди ответа.** Попросите длинный ответ, на середине нажмите «Stop ⏹»
   (так подписана та же кнопка, пока учитель говорит) → голос замолкает сразу, звучит сигнал конца,
   дальше учитель не говорит.
5. **(обязательно) Режим полёта посреди ответа.** Попросите длинный ответ («Tell me a short story
   about a cat.»). Когда учитель **уже начал говорить**, включите режим полёта → учитель дочитывает
   ответ до конца, но с какого-то места **другим голосом** (голос телефона); в конце сигнал конца.
   Выключите режим полёта, подождите 5 секунд, нажмите «Talk to Teacher 🎙️» и задайте новый вопрос →
   учитель снова отвечает голосом `verse`.
6. (желательно, если под рукой есть Bluetooth-наушники) То же, что пункт 1, в Bluetooth-наушниках →
   первый слог каждого куска не съедается; паузы чуть длиннее, чем в проводных.
7. **(обязательно) Выгрузка журнала:** подключить телефон по USB → в корне репозитория
   `tools/pull-log.sh` → файл `diagnostics/latest.log` приложить в чат архитектора.

Что архитектор проверит по журналу сам (просить пользователя не нужно):
`[Audio] reply output: usb, shield 0 ms`; строки `[Audio] group i/N: realtime, …` с RMS и пиком;
`[Network] realtime session ready in … ms` до первого ответа; `[Network] realtime group: … tokens …`;
`[Audio] cue: …` на каждый сигнал; `[Timing] … audible=…`; в пункте 5 —
`realtime unavailable (network: …): group k/N and the rest of the reply via android` и
`circle end: REPLY_FINISHED`; при старте — `android tts ready in … ms`; в пункте 4 —
`circle end: STOP_BUTTON`; расхождения сверки — `realtime mismatch`, если будут.

## Результаты ручной проверки (телефон пользователя, 2026-11-22)
Samsung SM-A526U, Android 13, проводные наушники USB. Журнал — `diagnostics/latest.log` пользователя,
новая сборка с 16:29. Сборка до исправления «dot» (0384d85).

**Что сказал пользователь:**
1. Обычный разговор — **пройдено.** Голос сменился на `verse`, паузы между кусками сохранились.
2. Длинный ответ — **пройдено, с двумя замечаниями.** Весь список по порядку, номера вместе с
   заголовками, ничего не пропущено, лишних пауз нет, голос один. Замечания:
   - (а) пауза между номером пункта и заголовком слишком маленькая: цифра сливается с первым словом
     заголовка;
   - (б) дважды прозвучало лишнее слово «dot», которого нет в ответе. **Исправлено** (0384d85), см. ниже.
3. Громкость — **лучше, приемлемо, но не как у других приложений.** Слушает на максимуме громкости
   телефона, учитель всё ещё заметно тише других приложений, хотя «сейчас уже стало нормально».
4. «Stop ⏹» посреди ответа — **пройдено.** Голос замолкает, звучит сигнал конца, учитель молчит.
5. Режим полёта — **пройдено.** Ответ дочитан до конца, голос сменился на голос телефона.
6. Bluetooth — не проверялось, пользователь проверит позже.

**Разбор журнала:**
- **Сессия Realtime.** Открывается при старте сервиса: `GET api.openai.com/v1/realtime -> 101 in
  1122 ms`, `realtime session ready in 1262 ms` — ещё до первого нажатия «Talk to Teacher 🎙️».
  Запасной движок: `android tts ready in 117 ms (engine com.samsung.SMT)`. Через 60 мин сервер закрыл
  сессию (`closed by server, code 1001 (open 3601099 ms)`). При следующей записи она переоткрылась
  за 1,4 с, без ошибок.
- **Выход и щит:** `reply output: usb, shield 0 ms` во всех ответах.
- **Время «конец записи → голос слышен»** (`audible`), 6 ответов: без поиска 3,9 / 5,6 / 6,0 / 7,4 с,
  с поиском 8,2 / 10,1 с; медиана 6,7 с (в S01b было 9,2 с плюс ≈ 1,2 с тишины в начале звука).
  Синтез первой группы (`audible − tutor`) — 0,79–0,87 с; в том же журнале на старой сборке
  `first_audio − tutor` было 1,5–2,7 с плюс 1,2 с тишины `tts-1`. Остальное — распознавание и учитель
  (S02b).
- **Группы Realtime:** готовы за 0,4–1,1 с (`ready in`), первый звук 0,35–0,9 с. Опережение
  успевало: после первой группы ни разу не было ожидания посреди ответа.
- **Сверка работает.** Ответ 1, группа 4/4: Realtime **ответил вместо прочтения** (`expected 4 words,
  heard 10`, 242 токена текста); повтор прочитал дословно — пользователь этого не услышал.
- **«dot» — причина.** `SpeechPlanner` (S01) оставляет после заголовка группу из одного знака:
  `1. **Make a plan**` → `:` → `write it down.`; так же `.`, `!`, `-`. В журнале: группа 10/32 и
  5/47 (`mismatch: expected 0 words, heard 1`), а в группах 5/32 и 20/32 Realtime дал почти тишину
  (−61 дБFS). Сверка пропускает такие группы: слов для сравнения нет. `tts-1` читал их молча.
  Исправление: группа без единой буквы или цифры в синтез не идёт, её пауза остаётся
  (`group i/N: no words, not synthesized`). Это заплатка в синтезе; саму нарезку стоит поправить в
  `SpeechPlanner` (вопрос ниже).
- **Громкость.** Realtime отдаёт голос на −21…−27 дБFS RMS, нормализация поднимает на 5–11 дБ до
  −16…−17 дБFS, пик до −1 дБFS. Голос телефона (Samsung) — −18…−20 → −16 дБFS. Ограничитель
  срабатывает на большинстве групп (пик ровно −1,0), поэтому RMS после него бывает −17…−18.
- **Режим полёта:** `realtime session closed: network: SocketException` →
  `realtime unavailable (network: SocketException): group 10/47 and the rest of the reply via android` →
  группы 10–26 голосом телефона за 0,1–0,6 с каждая (первая — 5,6 с: ожидание сокета). Дальше —
  «Stop ⏹».
- **Стоимость:** за проверку ≈ 90 групп Realtime; на группу в среднем вход ≈ 82 токена текста (из
  них 64 из кэша), выход ≈ 38 токенов текста и ≈ 42 токена звука — по ценам S00b ≈ $0,001 за группу,
  ≈ $0,09 за всю проверку. Чуть выше оценки ($0,0008): группы в реальных ответах длиннее, чем в пробе.

## Замечено за пределами этапа
- **`tools/probe/probe.py` синтезирует фразы ученика через `tts-1`** (`M_TTS_OLD`, подкоманды
  `transcribe`, `vadservice`, `latency`). После 2027-01-06 эти пробы перестанут работать; для пробы
  `semantic_vad` перед S03 (D12) нужен другой источник звука ученика (своя запись WAV — аргумент уже
  есть — или Realtime).
- `TrainerViewModel` по-прежнему играет последнюю запись ученика через `MediaPlayer` (отладочная
  кнопка). Это не голос учителя, я её не трогал.
- Если на телефоне при старте сервиса нет английского голоса, это видно только в журнале
  (`android tts unavailable`), а в разговоре станет ошибкой, только когда понадобится запасной синтез.
  Для D21 (голосовые ошибки в S02b) стоит заранее проверить строку `android tts ready` в журнале
  пользователя.
- Голос телефона читает короткие группы вроде «1.» по-своему, и сверить его прочтение нельзя
  (расшифровки нет).

## Вопросы к архитектору
- **Номер пункта сливается с заголовком** (замечание пользователя, пункт 2а). Сейчас «1. **Title**» —
  одна группа, и паузу внутри неё делает (или не делает) Realtime. Варианты: номер — отдельная группа
  с короткой паузой (≈ 250–400 мс), или номер словом с запятой («One, …»). Это нарезка `SpeechPlanner`
  и эталон пауз — решение архитектора.
- **Громкость** (пункт 3): поднять целевой RMS с −16 до −14 дБFS (или выше) и потолок пика оставить
  −1 дБFS? Ограничитель уже работает почти на каждой группе, так что громче — значит сильнее сжатие.
  Нужен эталон «как другие приложения».
- **`SpeechPlanner` создаёт группы из одного знака** (`:`, `.`, `!`, `-` после заголовка) — в
  синтезе они теперь пропускаются, но на экране и в счётчике групп остаются. Поправить нарезку?
- Записать в `ARCHITECTURE.md` новые интерфейсы: `Synthesizer` (`name`, `prepare`,
  `synthesize → SynthesizedSpeech`, `release`), `AudioOutput.prepareReply()` и
  `play(audio, shieldMs)`, а также щит «1200 мс, только Bluetooth и неизвестный выход»?
- Пользователь принял, что при отказе Realtime посреди ответа остаток читается другим голосом.
  Закрепить решением?
- Ограничения по времени Realtime (подключение 5 с, ответ на группу 8 с — дальше запасной синтез)
  выбраны по пробам с большим запасом. Пересмотреть их по журналу пользователя, вместе с таймаутами
  S02b?
