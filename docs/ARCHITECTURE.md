# Архитектура Listening Comprehension Trainer

Версия документа: 5 (2026-11-23). Меняет этот документ только чат-архитектор.
Исполнители этапов предлагают правки через свой отчёт.

## Цель приложения

Тренировка понимания английской речи на слух в голосовом диалоге с учителем.
Главная трудность ученика — слитная речь. Приложение делает её разборчивой
паузами между смысловыми группами и постепенно возвращает к естественной.

## Условия, которые считаем постоянными

- Платформа: только Android (Samsung, реальное устройство). CLI-версия удаляется.
- Ученик всегда в наушниках. Эхоподавление не делаем.
- Запись ведётся со встроенного микрофона телефона, а не с Bluetooth-гарнитуры,
  чтобы наушники оставались в режиме качественного звука.
- Ключ OpenAI на компьютере пользователя лежит в `credentials.properties` в корне
  репозитория (строка `APIkey=...`). Файл в `.gitignore`. Читать его могут только
  сборка и локальные скрипты; печатать, логировать и коммитить ключ нельзя.
- На телефоне ключ хранится только на устройстве.
- Запись микрофона — PCM 16 кГц моно (подходит детекторам речи и загрузке файла).
  Если звук понадобится отправлять в Realtime API, пересчёт в 24 кГц делается на лету.

## Целевая структура

```
UI (Compose)            только рисует состояние и шлёт команды
   │
ConversationController  живёт в foreground-сервисе; машина состояний диалога
   │
   ├── AudioInput       микрофон → поток PCM 16 кГц, моно
   ├── TurnDetector     «ученик говорит / замолчал / закончил реплику»
   ├── Transcriber      звук → текст
   ├── Tutor            история диалога, системный промпт, инструменты (поиск, погода)
   ├── SpeechPlanner    текст учителя → смысловые группы и паузы (чистый Kotlin)
   ├── SpeechPipeline   группы по порядку, опережение 3, сверка, повтор, запасной синтез
   ├── Synthesizer      name, prepare(), synthesize(text) → SynthesizedSpeech (PCM + расшифровка), release()
   │                    реализации: RealtimeSynthesizer (основной), AndroidTtsSynthesizer (запасной)
   └── AudioOutput      prepareReply() → щит в мс по выходу звука; play(audio, shieldMs); сигналы
```

Состояния контроллера: `Idle → Listening → Thinking → Speaking → Listening …`
плюс `Error` с голосовым сообщением и повтором последнего запроса.

Каждый компонент под контроллером — интерфейс. Смена модели или поставщика
означает новую реализацию интерфейса, а не правку контроллера.

## Что не так сейчас (исходная точка)

**Замер пользователя 2026-11-16 (Samsung, наушники, вопрос с поиском в интернете):**
от конца реплики ученика до первого звука учителя ≈ **3 с**, каждый промежуточный шаг ≤ 1 с.
Работает стабильно, жалоб нет. **Замер оказался неверным** — см. ниже, эталон теперь по журналу.

**Эталон по журналу S01b (2026-11-19 … 22, 31 круг, проводные наушники USB):** от конца записи
ученика до запуска первой группы учителя — медиана **9,2 с** (4,4 … 58,5 с); без поиска 7,2 с,
с поиском 9,7 с. Голос слышен ещё на ≈ 1,2 с позже (тишина щита в начале файла), а запись
кончается через 3 с после последнего слова ученика. Медианы этапов: распознавание 2,8 с
(растёт с размером WAV 44,1 кГц, выбросы 27 и 48 с), учитель 1,9 с без поиска / ≈ 5 с с
поиском (в том числе `delay(800)`), синтез первой группы 1,8 с (первая группа ждёт в общей
очереди из 20–80 параллельных запросов). Это эталон для инварианта 2 и цель для S02–S02b.

**После S02 (2026-11-22, 6 ответов, проводные):** медиана `audible` **6,7 с** (3,9 … 10,1 с).
Синтез первой группы 0,8 с вместо ≈ 3 с (с тишиной `tts-1`). Остаток — распознавание
(1,5–3,8 с) и учитель: у длинных ответов (≈ 1200 знаков) сам ответ пишется 3,5–4,5 с —
довод за потоковый ответ (S02c).

Замечено в том же замере (вне текущих этапов, учесть в S02):
- поиск в интернете не дал данных (`(Search attempted, fallback)`), а учитель всё равно
  уверенно назвал даты и подробности — возможная выдумка;
- служебная метка `(Search attempted, fallback):` стоит в начале текста учителя и
  **произносится вслух** (подтвердил пользователь) — метка должна быть только на экране;
- распознавание исказило слово (`Autouch` вместо `outage`).

- Цикл диалога размазан между `MainActivity` (запуск записи через `LaunchedEffect`)
  и `TrainerViewModel`. Вероятно, отсюда сбой в фоне: запись стартует из экрана.
- `TrainerViewModel.getTeacherReply` делает всё сразу: LLM, инструменты, разбиение,
  синтез, воспроизведение.
- Конец реплики: фиксированный порог 59 дБ и 3 с тишины; предела длины записи нет.
- Микрофон выключен, пока учитель думает и говорит.
- Имена моделей (`whisper-1`, `tts-1`, `gpt-4o-mini`) разбросаны по коду.

## Эталон озвучки (текущее поведение, «золотой стандарт» Android)

Перенесено из прежнего `AGENTS.md`. Менять значения можно только осознанно, с записью
в журнал решений; при правках сначала думать о понимании ученика, потом о естественности.

- Смысловая группа: 3–5 слов, **жёсткий предел 6 слов**.
- Скорость речи: 0,88.
- Паузы после группы:

  | Где кончается группа | Пауза |
  |---|---|
  | конец абзаца (`\n`) | 1600 мс |
  | жирный заголовок (`**…**`) | 1100 мс |
  | конец предложения (`. ! ?`) | 1000 мс |
  | `, : ;` | 600 мс |
  | перед союзом / внутри предложения | 250 мс |

- Номер пункта списка (`1.`) — отдельная группа, пауза после него **400 мс**, затем заголовок
  (D22; до S02b номер и заголовок были одной группой и сливались на слух).
- Группа всегда содержит хотя бы одну букву или цифру; одиночный знак (`:`, `.`, `!`, `-`)
  присоединяется к предыдущей группе (D23).
- **Щит Bluetooth.** Наушники засыпают в паузах и съедают начало следующей группы.
  С S02: 1200 мс локальной тишины (нули) перед группой и запуск группы на 1200 мс раньше —
  **только** когда звук идёт в Bluetooth или выход неизвестен. Проводные и динамик — без щита (D17).
- Громкость: голос нормализуется по звучащим окнам, пик не выше −1 дБFS; целевой уровень —
  в D25. Сигналы чуть тише голоса.
- Поведение учителя под уровни A2/B1/B2 не менять без явной задачи.

## Звуковые сигналы (с S01b)

Пользователь занимается, не глядя на экран (D13). Сигналы генерируются в приложении
(`audio/CueTones.kt`), когда играть — решает контроллер.

| Событие | Сигнал | Как звучит |
|---|---|---|
| началась запись (оба режима) | «говори» | две ноты вверх, 880 → 1320 Гц, 0,19 с; запись начинается после него |
| запись с речью закончена | «обрабатываю» | одна нота 660 Гц, 0,12 с |
| ждём учителя дольше 5 с | «тик» | щелчок 1200 Гц, 25 мс, на 10 дБ тише; каждые 3 с |
| идёт запись (с S03) | «пульс» | тихий короткий звук каждые 2 с, только в наушниках (D28) |
| ученик ничего не сказал | «не услышал» | две одинаковые ноты 494 Гц, 0,29 с |
| ошибка | «ошибка» | две низкие жужжащие ноты 196 → 185 Гц, 0,40 с; за ней всегда «конец» |
| разговор окончен, ждать нечего | «конец» | три ноты вниз 784 → 659 → 523 Гц, 0,42 с; на каждом выходе из круга |

## Инварианты (нарушать нельзя ни на одном этапе)

1. **Принцип чанков.** Речь учителя дробится на короткие смысловые группы.
   Укрупнение запрещено. Резать внутри устойчивого сочетания тоже нельзя.
2. **Скорость.** Время от конца записи ученика до первого слышимого звука учителя не должно
   расти. Меряется по строкам `[Timing]` журнала (медиана и худший случай), не секундомером.
   Цель после S02b: медиана ≤ 4 с без поиска и ≤ 6 с с поиском.
3. **Логика отдельно от Android.** Разбиение текста, машина состояний, правила
   конца реплики — чистый Kotlin с модульными тестами.
4. **Модели в одном месте.** Все идентификаторы моделей и адреса API — в одном
   файле конфигурации.
5. **Секреты.** Ключи, токены и записи голоса в репозиторий не попадают.
6. **Мелкие шаги.** Этап делает только то, что в его брифе.
7. **Приложение собирается** после каждого коммита в `master`.
8. **Журнал.** Каждый выход из круга пишется в журнал строкой `circle end: <ПРИЧИНА> (...)`.
   Формат строки: время с мс и поясом, `[Источник]`, событие. Источники: `Process`, `Activity`,
   `UI`, `Service`, `Controller`, `Timing`, `Audio`, `Network`, `Crash`. В журнал никогда не
   попадают ключ, тексты реплик, запросы поиска, имена устройств. Всё, что можно проверить по
   журналу, проверяется по журналу, а не просьбой к пользователю.
